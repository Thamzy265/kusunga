# M1.2 Clipboard history capture — design note

Date: 2026-11-03 — Size: large — new local data store, personal data (everything the user copies), new native code — Phase: MVP — Status: approved by PM 2026-11-03

## Context

Plan item M1.2 (`docs/PLAN.md`). Kusunga must keep what the user copies so they can paste it again. M1.1 gave us a Flutter desktop app with a window and a menu-bar/tray icon. Nothing is stored yet. The picker and paste come in M1.3, snippets in M1.4. This item builds the capture, the store, and a simple history list in the main window so the user (and QA) can see, delete and clear what was saved.

## Requirements and non-goals

- Functional:
  - Text and links copied in any app appear in history within 1 second.
  - History keeps the newest N items. N is set in the app (default 200, range 10–5,000). The oldest item is removed when the limit is reached.
  - Copying the same text again moves the existing item to the top instead of saving it twice.
  - History is stored encrypted on disk, with the key in the OS keychain.
  - Items that password managers mark as secret are never saved (pulled forward from M1.6, because saving passwords even for one milestone is not acceptable).
  - The user can delete one item and clear all history (privacy is never deferred; the full "Delete everything" and export stay in M1.8).
  - Data is saved safely on every exit path: tray Quit, Cmd+Q, Dock Quit, Windows logoff and shutdown.
- Non-functional:
  - No network use. No content in logs.
  - Capture costs less than 1% CPU when idle.
  - Works with keyboard and screen reader (history list).
- Non-goals: images and files (Later line), picker and paste (M1.3), snippets (M1.4), app ignore list and pause (M1.6), auto-expiry (M1.7), export (M1.8), sync (M3).

## Top 3 qualities

| Quality | Target | How we check it |
|---|---|---|
| Confidentiality | History file unreadable without the keychain key; secret-marked copies never stored; no content in logs | Test opens the DB file without the key and fails; tests with concealed/transient/excluded formats store nothing; log test greps for test content |
| Data integrity | Never more than N items; no duplicates; no lost writes on quit; a schema change never loses data | Property tests on the limit and dedupe; quit-path tests; migration tests from every earlier schema version |
| Responsiveness | Copied text in history ≤ 1 s (p95); idle CPU < 1% | QA timing on the real app; Activity Monitor / Task Manager reading |

## Estimate

Trivially small: one user per install, about 50–500 copies a day, at most 5,000 items. Text items are capped at 1 MB each (larger copies are skipped and counted). Worst case on disk about 50 MB, typical under 1 MB. Writes: a few per minute. Reads: the list view and (M1.3) the picker search.

## Data

- Storage: one SQLite database in the app's support folder (`~/Library/Containers/com.wnasoni.kusunga/Data/Library/Application Support/` on Mac, `%APPDATA%\Kusunga\` on Windows), encrypted as a whole with SQLite3 Multiple Ciphers through `package:sqlite3` 3.x build options. See ADR 0002.
- Key: 256-bit random key created on first run, stored in Mac Keychain / Windows Credential Manager via `flutter_secure_storage`. Never written to disk or logs.
- Table `clip_items`:
  - `id INTEGER PRIMARY KEY`
  - `content TEXT NOT NULL CHECK (length(content) BETWEEN 1 AND 1048576)`
  - `kind TEXT NOT NULL CHECK (kind IN ('text','link'))`
  - `content_hash BLOB NOT NULL UNIQUE` (SHA-256 of the content, for dedupe; inside the encrypted DB)
  - `created_at INTEGER NOT NULL`, `last_copied_at INTEGER NOT NULL` (Unix ms)
  - index on `last_copied_at DESC`
- Setting `history_limit` in a `settings` table (key/value), with a CHECK on the range.
- Transactions: insert-or-bump and trim-to-limit happen in one transaction, so the limit always holds.
- Not stored: the source app. It is read at capture time only (for the secret check now and the ignore list in M1.6) and then dropped. This keeps the record of which apps the user uses off disk.
- Schema changes: `PRAGMA user_version`; forward migrations only, each in a transaction, each with a test from every earlier version. Expand → migrate → contract when a column changes. Before a migration the app copies the DB file to `kusunga.db.bak` and removes the copy after success.

## Options

### A: Our own small native clipboard plugin + encrypted SQLite (recommended)

- Mac (Swift): poll `NSPasteboard.general.changeCount` every 250 ms. Reading the count does not read content. On a change, check the pasteboard types first; skip if `org.nspasteboard.ConcealedType`, `org.nspasteboard.TransientType` or `org.nspasteboard.AutoGeneratedType` is present; otherwise read the plain string.
- Windows (C++): `AddClipboardFormatListener` and `WM_CLIPBOARDUPDATE`. Skip if `ExcludeClipboardContentFromMonitorProcessing` is present, or `CanIncludeInClipboardHistory` is 0, or `Clipboard Viewer Ignore` is present; otherwise read `CF_UNICODETEXT`.
- Both send `{text, concealed: bool}` over an event channel. Dart decides kind (link vs text), dedupe, and storage.
- Benefits: we control exactly which formats are checked (the core of our privacy promise); small code; no extra build tools.
- Costs: about 150 lines of Swift and 200 lines of C++ to maintain; native code needs native tests and QA on both OSes.

### B: `clipboard_watcher` + Flutter `Clipboard.getData`

- A pub.dev package tells us something changed; Flutter reads the text.
- Benefits: less native code.
- Costs: Flutter's text read cannot see the secret-marker formats, so passwords from password managers would be saved. That breaks a requirement. We would still need native code for the check, so we would have two moving parts instead of one.

## Decision

A. B cannot meet the "never save secret-marked copies" requirement. Hard to reverse: the storage format and encryption (ADR 0002). The native plugin is easy to change later and needs no ADR.

## Failure plan

No outbound calls, so no network timeouts or retries.

- Keychain unavailable or key missing: never fall back to a plaintext file. History runs in memory only for this session, and the window shows a banner: "History won't be kept after you quit, because Kusunga can't reach your keychain." (PM decision 2 on the deck.)
- Key present but DB cannot be opened (wrong key, corrupt file): move the file aside as `kusunga.db.unreadable-<date>`, start a new empty DB, and tell the user once: "Kusunga couldn't read your old history, so it started a new one."
- Disk full or write error: keep the item in memory, retry once on the next copy, show the error banner; never crash.
- Clipboard read fails (another app holds the Windows clipboard): retry up to 3 times, 50 ms apart; then skip that copy.
- Copy larger than 1 MB: skip it and do not store any part.
- Exit paths: Dart writes each item in its own transaction as it arrives (no pending buffer), so a sudden quit loses at most the copy in flight. Mac `applicationShouldTerminate` and Windows `WM_QUERYENDSESSION`/`WM_ENDSESSION` call a Dart `flush` that closes the DB cleanly.
- macOS pasteboard privacy: Apple has a "Paste from Other Apps" setting (Ask / Allow / Deny) in Privacy & Security, previewed since macOS 15.4; whether it is on by default in macOS 27 is not confirmed. At start-up the app reads `NSPasteboard.general.accessBehavior` (macOS versions that have it). If it is not "always allow", the window shows a setup card that explains why Kusunga needs it and how to allow it in System Settings (Apple asks apps not to deep-link from the alert itself). QA checks the real behaviour on macOS 27.0.1.

## Observability

- Local log file (rotated, max 1 MB) with error codes only: no clipboard content, no hashes, no app names. A test copies a unique marker string and checks it never appears in the log.
- Two numbers to watch in QA: capture latency (copy → item visible) and idle CPU.
- n/a — no health endpoint or dashboards (local app, no telemetry per decision D3).

## Trust boundaries and abuse cases

- Boundaries:
  1. Clipboard content from any app (untrusted text, any size, any characters).
  2. Other processes running as the same user (can read files in the user's folders).
  3. The OS keychain.
  4. Backups (Time Machine, OneDrive folder sync) that copy our files.
- Abuse cases:
  - As malware running as the user, I copy the history file so that I can read everything the user copied — mitigation: whole-DB encryption; the key is in the keychain, bound to Kusunga's app identity.
  - As an attacker, I put a 500 MB string on the clipboard so that Kusunga runs out of memory — mitigation: Windows reads the size before copying; Mac checks length; anything over 1 MB is skipped.
  - As a website, I copy text with control characters, bidi overrides or HTML so that the history list misleads the user or runs code — mitigation: render as plain text only, never as HTML or rich text; show bidi and control characters as visible symbols; links are never opened automatically.
  - As a password manager user, I copy a password so that it ends up in history — mitigation: secret-marker formats are checked natively before the content is read.
  - As someone at an unlocked computer, I open Kusunga to read history — mitigation: out of scope for M1.2 (same as any open app); "Clear history" is one click; a lock option is a Later line.
  - As a log reader, I read Kusunga's logs to get clipboard content — mitigation: no content in logs, enforced by test.

## Rollout and rollback

- First version of the store (schema version 1), so no migration this time. The app creates the DB on first launch.
- Behind no feature flag: the history list is the main window's content from now on.
- Rollback: revert the merge. The DB file remains in the app support folder; an older build ignores it. To remove it, the user (or QA) deletes the app support folder and the "Kusunga" keychain item. Confirm by launching the old build: the placeholder screen shows.
