Update the encryption library, window and tray packages

Nothing should change for users. Under the hood: a newer encryption library and a new native layer for the window and tray.

Use the arrow keys to move between slides · Print to save as PDF

Problem and users

Three packages are behind, and Flutter 3.50.1 now lets us update them

Who

Everyone who uses Kusunga: their history is protected by the encryption library, and the tray and window are how they reach the app.

The job

Stay on current, maintained versions: sqlite3 3.9.2, window_manager 0.7.1, tray_manager 0.9.1.

Today's pain

We are on versions from before Flutter 3.50. Fixes since then, such as a Windows tray memory leak, don't reach us.

Success measure

Existing history opens unchanged with its key; tray and window work exactly as today; all checks and both CI jobs pass.

Design note: docs/design/package-updates.md · ADR 0009 (proposed).

Scope

Two separate parts, of very different shape

sqlite3 3.5.2 → 3.9.2

  • Encryption library SQLite3 Multiple Ciphers 2.5.0 → 2.7.0 (SQLite 3.53.4 → 3.54.1)
  • Same encryption format; existing databases should open with the existing key
  • No app code change; about 12 files of version text, licence notices and tests

window_manager and tray_manager

  • Rebuilt on a new C++ core, nativeapi, compiled during the build
  • The old way of calling them still works but is marked for removal, and our check fails on that
  • 2 app files (about 17 calls) and 2 test files to rewrite

Not in this item: other packages, new window or tray features, an Intel Mac build.

Data and privacy

The history stays encrypted the same way

What changes

Only the version of the library that encrypts and reads the history file. No new data, no new store, no network at run time.

How we prove it

  • Test databases in the old format (from M1.10a) must open on the new library
  • A wrong key must still fail
  • QA opens the qa test profile's real file

If it ever fails

The app already shows its "can't open your history" screen and never overwrites the file. Undo is reverting the change.

Options

Two choices: how to split it, and how to call the new packages

Split

  • A: two items with their own pull requests: sqlite3 first (M1.10b), then window and tray (M1.10c)
  • B: one branch for all three, as the plan says today

Window and tray

  • A: rewrite our 2 small connector files on the new API; tests use a fake so they never create a real tray icon
  • B: keep the old API and switch off the "deprecated" warning in those 2 files: smallest change, but a weaker check and code that will be removed upstream

Recommendation

Split A and API A: the data-safety part is checked on its own, and the check stays strict with no switched-off warnings.

Security

New code comes in from two places; both are pinned

Trust boundaries

  • The encryption library binary, downloaded from GitHub during the build
  • New packages from pub.dev, including C++ source built on our machines and in CI

Abuse cases

  • A swapped encryption library binary
  • A look-alike or hostile package version

Mitigations

  • The package checks the binary's SHA-256; we record the 4 expected values and QA compares one
  • Lockfile hashes and the strict install in CI; verified publisher (the same one as today); reviewer scans the C++ for network or process calls
