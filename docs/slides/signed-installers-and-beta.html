Signed installers and first beta

Testers can install Kusunga on Mac and Windows with no security warnings, and see its version, licence and source.

Use the arrow keys to move between slides · Print to save as PDF · Design note: docs/design/signed-installers-and-beta.md · UI spec: docs/ui/about-and-licences.md · ADR 0006, 0007 (proposed)

Problem and users

Kusunga works, but nobody else can install it safely yet

Who

5–20 invited beta testers on Mac and Windows, and you.

The job they are doing

Download Kusunga, install it, use it every day, and tell us what breaks, naming the exact version.

Today's pain

Builds aren't signed, so macOS and Windows block or warn. The Mac release build fails on macOS 27. There's no licence screen, which the GPL needs, and the Mac history key is in the weaker login keychain.

Success measure

0 install warnings on a clean account · 0 history items lost when updating · every shipped file tied to one public git tag.

Facts from main at 02369fb (scout lookup, 2026-11-19). Plan acceptance criteria AC1–AC10 are in the design note.

Scope for this phase

Six parts, each through every gate

In M1.9

  • a About section in Settings: version, copyright, GPL notice, source link, every licence
  • b Mac release build fixed for macOS 27; Hardened Runtime; a guard that the test-only switch never ships
  • c Mac history key moved to the data-protection keychain, losing nothing
  • d Windows installer, signed on the route you choose
  • e Release script, checks, release notes, rollback plan
  • f Short DPIA for you to sign

Deferred (Later lines with triggers)

  • Release in GitHub Actions, trigger: > 2 releases a month for 2 months, or a second releaser
  • Auto-update, trigger: > 50 beta users, or ≥ 5 reports of testers on an old build
  • Intel Mac build, trigger: ≥ 5 requests from Intel Mac users
  • Build sqlite3mc from source, trigger: a cipher CVE in a pinned build, or a change to the package's prebuilt scheme

Not in M1: Mac App Store, Linux, crash reports, website, mobile, sync. All slides apply.

Options

Where releases are signed

Option A: release script on your Mac

  • Signing keys never leave your machine; nothing secret on GitHub, which matters now the repo is public
  • Only you can cut a release, and you run the script
  • Small–medium effort

Option B: GitHub Actions with signing secrets

  • Repeatable, with no set-up on your Mac per release
  • Signing keys live in GitHub; a leak lets anyone sign malware as you
  • Medium effort

Recommendation

Option A for the beta, because the keys stay with you and a handful of releases doesn't need automation. B is a Later line.

Security

Protect the download and the signing keys

Trust boundaries

  • Your signing keys and build machine
  • The download place
  • The prebuilt encryption library
  • The key move (reads an old keychain item)

Abuse cases

  • Swap the download for a trojaned build
  • Steal the signing key and sign malware as Kusunga
  • Ship a build with the test-only key switch on
  • Weaken the cipher with a changed library binary

Mitigations

  • Signed and notarised builds; SHA-256 of every file on the release page
  • Keys only on your Mac (option A)
  • The release fails if the switch is in the binary
  • Library pinned by SHA-256 and re-checked in the shipped file

Release checks: codesign --verify --strict, spctl, stapler validate, a strings check, an extensionfunctions check, a Windows signature check. A failed check stops the release.

Decisions needed

7 decisions for you

D1. Windows signing

A: Microsoft Store (free; Microsoft signs) · B: SignPath Foundation (free for open source; early warnings) · C: an OV certificate (about $150–300 a year) · D: unsigned (testers see a warning; needs your risk acceptance)

Recommendation: A, with B as the fall-back. A changes launch at login and the data folder on Windows, so they are re-tested.

D2. Encryption library

A: keep the SHA-256-pinned prebuilt · B: build it from source

Recommendation: A, because it's hash-pinned and each shipped file is re-checked.

D3. Mac build

A: Apple silicon only · B: Universal (also Intel); needs a Flutter update

Recommendation: A, because macOS 27 only runs on Apple silicon. Intel waits for requests.

D4. Beta size and download place

A: 5–20 testers via GitHub Releases (pre-release) · B: the same testers, files shared privately by you

Recommendation: A, because the source and checksums sit next to the files.

D5. Version number

A: 0.9.0 · B: 1.0.0-beta.1

Recommendation: A; save 1.0.0 for the public release.

D6. Release process

A: script on your Mac · B: GitHub Actions with secrets

Recommendation: A, because the keys stay with you.

D7. Feedback and tester data

A: email to an address you choose · B: GitHub issues (public) · C: both, with a "no clipboard content" rule

Recommendation: A. Also needed: the lawful basis and retention for tester details and feedback.

Nothing is assumed: the developer starts parts a, b and f only after you approve this deck. The Store's hidden-listing details and SignPath eligibility are not yet confirmed.
